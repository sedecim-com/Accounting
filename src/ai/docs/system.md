# System overview

## Architecture
Multi-tenant (tenant → organization → MX/USA legal entities). Ledger operations are scoped by entity_id: the `x-entity-id` header CHOOSES among the entities listed in the JWT and cannot add one (403 otherwise). Tenant-level configuration — webhooks, integrations, PAC preferences, blockchain config — is scoped by tenant_id only. Standards: MX NIF / US GAAP / IFRS per entity. REST API /v1 (JWT + granular permissions). GraphQL exists at /graphql but is OFF unless GRAPHQL_ENABLED=true, and it is mounted outside the audited /v1 prefix (no audit_log row with IP and user agent) — do not tell a user the GraphQL API is available without confirming that flag. Prometheus metrics at /metrics; health at /live and /ready (/health is a legacy alias). Those three serve without auth.

## Modules and their docs
accounting (journal entries/periods), receivables (customers/invoices), payables (vendors/bills), banking (reconciliation), mexico-cfdi (stamping/ingestion), payroll (MX+USA), reports, mnemosine (your flow), playbooks (how to GUIDE each process), cli-reference (exact command surface), identity-access (login/RLS/roles), connectivity (database hosting + model providers), external-integrations (other accounting systems). The NIF and IFRS normative docs (nif-*, niif-*) are in the read_docs index, not in this list.

## Events (outbound webhooks)
A subscription may name any event in WEBHOOK_EVENTS: journal_entry.*, invoice.*, cfdi.stamped/cancelled, bill.*, payment.received/made, bank_transaction.*, reconciliation.completed, period.soft_closed/hard_closed, account.*, payroll.run.calculated/approved/paid, paycheck.issued, cfdi_nomina.stamped, tax_form.filed. ONLY THREE ARE EVER EMITTED: payroll.run.calculated, payroll.run.approved and payroll.run.paid. Nothing else calls dispatchEvent, so a subscription to invoice.paid, payment.received or bank_transaction.matched is accepted and never fires — say so before a user builds on it. Delivery is fire-and-forget; a failed one is retried with per-subscription backoff (webhook_subscriptions.retry_config) only when `mnemosine subscription delivery sweep` runs — a command meant for cron, not a resident worker. Human: POST/GET/DELETE /v1/webhooks, /:id/test, /:id/deliveries, /deliveries/:id/retry. /:id/test answers {sent:true} and delivers nothing: it dispatches test.ping, which is not in WEBHOOK_EVENTS, so no subscription can carry it.

## Integrations (admin)
- Mexico PACs: FOUR registered — Sovos/Reachcore, Finkok, SW Sapien, Edicom — with failover, circuit breaker and preferences (GET/PUT /v1/admin/integrations/pac/preferences/all). The default chain is finkok → sw_sapien → edicom, and those three are simulators the anti-simulation lock forbids from stamping. Stamping is de facto off until a real PAC is contracted: see mexico-cfdi.
- Payments: the Stripe and Conekta adapters store credentials and report healthy, but they FABRICATE their responses (charge ids from crypto.randomBytes) and nothing in the system calls createCharge — no money can be collected through them. Files: the S3 adapter is the same kind of stub, with no AWS call. Banks: Plaid/Belvo are config keys and nullable columns; NO connector exists. Email was retired in F03 (the adapter faked the send): POST /v1/invoices/:id/send issues the invoice and records invoices.sent_to, it transmits nothing.
- Per-provider health with circuit breaker: GET /v1/admin/integrations/health/all. GET /v1/admin/integrations publishes a `simulado` flag per PAC adapter.

## Blockchain attestation (optional)
Off unless the tenant has an ACTIVE blockchain_config row; with one, every posted journal entry is hashed and attested (hash → configured chains + Bitcoin anchor). THE ANCHOR IS SIMULATED TODAY: every chain adapter, the zkVerify client and the Bitcoin anchor fabricate their txids, and every row is written is_simulated=true — never tell a user their ledger is anchored on a chain. Admin config: /v1/admin/blockchain/config, /bitcoin/config, /commit-period, /publish-aggregates; /commit-period refuses to seal a period while any posted entry still lacks its entry_hash. Public verification without auth: /public/v1, served only with PUBLIC_VERIFICATION_ENABLED=true, and even then it answers 501 ATTESTATION_SIMULATED for a simulated attestation — which today is all of them.

## Audit
Every HTTP request carries an x-request-id (an inbound header is honored, otherwise one is generated; it is echoed as X-Request-Id and attached to every log line). ON /v1 THAT IS NOT THE ID IN THE ANSWER: the audit middleware overwrites the header with a fresh uuid before any route runs, so the `meta.request_id` of the body and the audit record carry a DIFFERENT id from the X-Request-Id header and the logs. Correlate by the response header; never tell a caller the id they sent will come back in the body. Your actions are recorded in ai_drafts and ai_questions: drafts carry ai_model, ai_confidence, ai_reasoning and user_request; questions carry ai_model and user_request only — no confidence and no reasoning column.
